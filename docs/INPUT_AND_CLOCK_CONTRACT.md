# 输入与时钟契约：Flash 游戏联机实验

状态：**基于源码静态证据制定的实验约定，尚未证明原游戏已经遵守或运行通过。**

目标是让实验保留原有操作与时序语义，同时让输入可归属、可重播、可检查。网络模型、替代物理演示、原游戏运行验证必须分别报告。

## 1. 三种频率不能混淆

必须分别记录舞台/逻辑帧、物理步长、网络状态发送频率。浏览器渲染帧率又是单独的表现参数。

| 样本 | 源码证据 | 含义 |
| --- | --- | --- |
| 森林冰火人 1 | `decompiled/1-export/script/scripts/Game.as:23` 的 SWF 元数据声明 25 FPS | 舞台声明帧率 |
| 森林冰火人 1 | 同目录 `level.as:76` 为 `m_timeStep = 1 / 26` | 每次物理更新所用步长；不证明舞台以 26 FPS 运行 |
| 森林冰火人 1 | `level.as:929` 注册 `ENTER_FRAME`，1804 调用 `m_world.Step` | 帧驱动规则与物理 |
| 闪翼双星正传 | `wck/World.as:58` 默认步长 0.05；143、405–416 绑定帧并推进物理 | 默认一次帧回调一次物理推进 |
| 闪翼双星正传 | `Level.as:718–719` 把步长设为 0.02、舞台设为 15 FPS | `boom` 慢动作模式 |
| 闪翼双星正传 | `Level.as:709–715、726` 按帧计数并恢复步长 0.05、舞台 30 FPS | 30 是代码中的恢复帧率，未从缺失的 SWF 包头读取初始值 |

冰火人路径相对于 `02-fireboy-watergirl/`；闪翼路径相对于 `01-shanyi-binary/core-decompiled/script/scripts/`。冰火人 2/3/4 的 `Game.as` 第 26/27/37 行也声明 25 FPS；相应 `level.as` 第 66/72/107 行的物理步长均为 `1/26`。后三部还存在第二个 `m_lworld` 的物理更新，分别见 `level.as` 第 4262/5487/4801 行；适配器不能只推进其中一个世界。

**25 FPS 与 1/26 秒不能擅自归一为同一个数。** 闪翼的 30/15 FPS 与 0.05/0.02 也不能仅靠改变网络广播频率来代替。首次验证应保留源码语义，以实际运行基准为准；统一调到 60 Hz 属于玩法迁移，需要单独回归。

## 2. 房间和席位拥有输入归属

每条操作须绑定已认证连接与服务器分配的席位。客户端消息可以含输入序号、动作状态、边沿事件和指针信息；客户端自报的另一个 `playerId` 不应改变服务器所认定的操作者。

建议保持以下逻辑字段，而不绑定某个网络库的序列化格式：

| 字段 | 用途 |
| --- | --- |
| `sessionEpoch` | 区分重新加入、重新开局前后的输入世代 |
| `inputSequence` | 每个席位内递增，识别重复或旧操作 |
| `heldActions` | 当前持续按住的动作，如 left/right/up/down |
| `edgeEvents` | 有独立事件编号的按下/松开/点击，保留短按 |
| `pointer` | 可选；明确是世界坐标、归一化坐标还是相对累计位移 |
| `assignedTick` | 由权威端记录实际应用在哪个逻辑 tick，不能直接信任客户端声明 |

语义版本和游戏版本应在入房时校验。不要让客户端直接设置角色位置、生命值或胜负结果。

## 3. 持续状态与边沿必须都保留

闪翼 `misc/Input.as` 的语义：

- `keysDown / kd`：当前按住。
- `keysPressed / kp`：本帧刚按下。
- `keysUp / ku`：本帧刚松开。
- 108–122、124–155 处理转换；158–205 在帧末清理边沿。

`hero/Hero.as:1333–1336` 左右读 `kd`，跳跃等读 `kp`；还有双击与攀爬分支，因此仅传一个周期性的按键位图可能漏掉短按。

冰火人 1 则在 `Game.as:663–704、822–843` 维护按住布尔值；`level.as:1440–1450` 使用 `u_pressed` 配合 `prohibjump1` 锁存跳跃，第二角色在 1587–1596 有对应逻辑。**这是持续输入加按下锁存，不能错误改成“按住后每 tick 自动再跳一次”。**

每个受控逻辑 tick 建议遵循：

1. 收集并校验属于本 tick 的各席位输入；确定清晰的迟到输入策略。
2. 更新按住状态，建立本 tick 的按下/松开事件。
3. 执行该游戏完整的玩法更新序列。
4. 采样权威状态、事件和应用过的输入序号。
5. 清除本 tick 的边沿状态，保留持续按住状态。

这个顺序是待适配器实现的契约，不表示仅调用一个物理函数已经完成第 3 步。输入收包频率、绘图帧率和边沿清理次数不能相互替代。

## 4. 短按、丢包、失焦与重连

- 一次按下后立刻松开，即使两者发生在两次状态采样之间，也应有事件记录。
- 重复事件只能应用一次；已经跨过有效窗口的旧事件不能在很久后突然触发。
- 客户端失焦应主动发送释放；连接关闭和输入租约超时由权威端释放该席位操作，不能依赖一条必达的松键消息。
- 重新加入时生成新输入世代、补发完整状态、清空旧边沿，并重新确认席位。旧连接迟到消息不能继续操纵角色。
- 断线策略必须明确。本实验暂停整房，因此暂停时清空两席位的未消费输入，恢复后接收新输入；若以后改为另一位玩家可以继续游戏，则只释放断线席位。

以上是网络输入层需要执行的行为。它不保证任意 Flash 游戏已经具备完整状态保存/恢复能力，也不等于服务器重启后能恢复对局。

## 5. 控制物理不等于控制完整游戏

森林冰火人 1 的 `level.as:1598` 有帧计数；1657–1658 的风力计算用到该计数；1705–1730 的门动画帧参与胜负。`Game.as:328–357` 还通过 `getTimer()` 计算成绩。

闪翼存在多个 `ENTER_FRAME` 回调、动画帧判定、显示列表碰撞、敌人随机决策及慢动作切换。仅暂停 `World.step` 而让 MovieClip 时间轴或其他帧回调继续运行，可能已经改变玩法状态。

若实验采用多个原运行时的输入同步，应首先证明：

- 玩法初始化、关卡数据与版本一致。
- 所有有效帧、时间轴、定时器与相关事件顺序可以受控。
- 玩法随机数和时间来源可以一致重播。
- 状态摘要足以覆盖角色、动态物体、机关、敌人、随机状态与影响玩法的动画状态。

若这些条件不能成立，就不应把“按键广播成功”称为确定性联机成功。服务器权威状态同步可以避免要求各客户端模拟完全一致，但依然需要提取规则、状态及可应用状态的显示层。

## 6. 实验验收与报告措辞

| 实验 | 至少核查什么 | 可以证明什么 |
| --- | --- | --- |
| 输入模型 | 两席位隔离、短按、按住、松开、重复包、过期包、失焦与重连 | 输入契约是否成立 |
| 独立网络实验 | 双客户端、权威结果、完整快照、丢包/延迟注入 | 该实验实现的网络行为 |
| 原包播放基准 | 未修改游戏可加载、可操作、可完成关卡 | 当前运行时对该包的实际兼容性 |
| 原游戏输入桥 | 真实两角色接收网络输入、原有动作保持 | 输入桥已接入原游戏 |
| 原游戏同步 | 完整场景中机关、随机、动画、胜负一致，异常恢复正确 | 指定版本与测试条件下的联机结果 |

当前静态审计只完成入口与风险定位。演示用几何体、移植后的简化规则、网络模型或测试专用 Flash 程序均应单独标明；它们不能替代两款原游戏的运行验收。
