# 公网联机与延迟优化方案

## 2026-11-25 PCSERVER 部署

PCSERVER 的 `D:\GameLobby` 运行局域网大厅、公网大厅、格斗服务和 FRP。四个 Windows 任务以 `LOCAL SERVICE` 开机启动。公网保留 `10011–10015` 的已有映射。FRP 客户端使用中继已经开放的 QUIC `7001` 控制通道。局域网通过 `10.13.24.1:8787` 访问。

两个大厅分别使用 `data\rooms-lan.json` 和 `data\rooms-public.json`。首页的局域网按钮由浏览器实测连通性后启用。公网 HTTP 页面受到浏览器的局域网访问限制时，可从局域网直接打开局域网入口。

公网死神 vs 火影通过大厅同源的 `/bvn33/` 加载页面、游戏资源和 WebSocket。原 `10015` 入口可访问兼容页面。服务按每个玩家的 WebSocket 往返延迟调节待确认窗口，对战引擎逐帧检查同步。迷宫坦克优先走大厅同源 `/tank-match`，连接失败时可用原席位在 `10011` 和 `10012` 之间重试。两款游戏均在进入对局前检查入口，加载失败时在房间或游戏页提供重试。

## 2026-11-24 公网测试实例

公网入口为 `http://39.108.93.52:10011/`。已恢复的 FRP 映射覆盖网页、大厅和坦克、冰火人权威通道、闪翼双星镜像、死神 vs 火影，依次使用 `10011–10015`。公网实例与局域网实例独立保存房间，任何加入同一公网房间的玩家都应从公网入口进入。FRP 客户端使用无线网卡连旧服务器，并给网页、大厅和格斗服务配置了 TCP 健康检查。

公网实测覆盖坦克双人开局、双向操作和刷新恢复，持续收帧窗口 40 秒，每端 888 帧，未记录浏览器或 WebSocket 错误。冰火人和闪翼双星分别验证了双方实际操作。第二间闪翼房通过大厅端口回退时，协议测试收到双方就绪消息。

## 原有方案和历史记录

当前版本面向本机/可信局域网：`local/serve.mjs` 默认监听 `0.0.0.0`，页面使用自动探测的局域网 IPv4。它没有 TLS、没有公网身份认证，也还没有按公网 RTT 调优，**不应直接把 8787/8788 暴露到公网**。

2026-11-19 运行状态：本机与局域网入口正常；独立 `frpc` 进程连续收到 frps 的 `EOF`，`39.108.93.52:10001–10004` 当前不可用，因此生产启动默认使用局域网地址。恢复公网映射前必须确认 frps 服务和 token 可用，再按本文件配置 TLS/反向代理。

公网版本按下面的顺序落地，避免把局域网方案直接放大成不安全的公网服务。

## 1. 传输层

- 在反向代理（Caddy/Nginx/Cloudflare Tunnel 等）终止 TLS，只暴露 `https/wss`；源站 8787/8788 继续只监听内网或回环。
- WebSocket `/lobby` 与游戏 authority 的 `/ws` 都走 WSS。
- 公网入口至少要有房间级访问控制；现有房间密码只保护加入流程，不能替代公网入口防护。
- 建议给每个房间签发短期会话凭据，由反向代理或大厅服务校验；不要复用局域网里的内部座位 token 作为公网访问凭据。

## 2. 权威与中继拓扑

- HTML5 游戏保持“单个 headless Chromium authority + 客户端投影”，不改成视频串流。
- 公网部署时把 authority 放在离玩家更近的区域节点；大厅只做匹配和路由，不承载游戏画面。
- 同一房间的 authority 与两个客户端尽量落在同一区域；跨区域时优先让 authority 靠近延迟最低的玩家，另一名玩家走区域中继。
- Shanyi 仍是实验性输入镜像，不承诺公网下的确定性同步；公网产品应优先把它标识为“实验模式”。

## 3. 延迟与抖动

- **自适应快照频率**：按 RTT/丢包动态选择 15–30 Hz；局域网默认 25 Hz（当前约 20–23 Hz 实测）。不要盲目提高到 60 Hz，上行带宽和 authority 主线程更贵。
- **插值缓冲**：客户端保留 60–120 ms 的 snapshot buffer；公网将当前 `smoothingMs`（约 55 ms）按实测 RTT 调到 80–120 ms，并保留 300 px 大修正立即 snap。
- **输入预测与校正**：本地只对“自己的角色”做轻量预测；收到权威快照后按误差平滑回正。当前 HTML5 观战端已加入仅自己角色的像素级预测偏移，物理和碰撞仍由权威端决定；它不是完整 rollback，公网版本仍需单独实现并测试。
- **快照压缩**：把 JSON 快照改为按字段 delta + 数值量化；静态地图/实体 id 只发一次。优先使用二进制编码（如 MessagePack/自定义 buffer），避免每帧重复长字段名。
- **合并输入**：输入端按 20–30 ms 批量，只发边沿和变化值；保留 `ackSeq` 用于丢失重放。
- **ack/重传**：WebSocket 有序可靠，但仍要记录最后确认的 input seq；断线重连时从最后一个权威快照恢复，不重放整局输入。

## 4. 大厅与匹配

- 房间广场查询和房间 WebSocket 分离；广场轮询降为 3–5 秒或 SSE，不在每个客户端每帧刷新。
- 匹配服务只维护房间元数据；游戏 authority 生命周期独立，空闲/无人会话自动回收（当前已加入 `SESSION_IDLE` 与 30 秒半启动回收）。
- 公网需要按区域、游戏、容量做筛选；现有 `seats` 容量字段（1–4）可作为匹配约束。

## 5. 监控指标

每次会话至少记录：RTT、快照频率、快照大小、输入到权威的延迟、插值缓冲、掉线/重连次数、authority 启动耗时。验收目标先定为：

- 同区域：P95 输入到画面 < 120 ms；
- 跨区域：P95 < 220 ms，且不出现持续漂移；
- 快照平均 < 8 KB/帧（双人）；
- 断线 5 秒内可回到房间，不丢失存档。

## 6. 与当前代码的接口

- `server/html5-research-room.mjs`：authority 的 tick 与快照捕获入口，后续在这里加自适应频率和 delta 编码。
- `adapters/fireboy-html5/state-snapshot.mjs`：快照字段来源，新增字段时要同步更新压缩 schema。
- `adapters/fireboy-html5/spectator-projection.mjs`：客户端插值/摄像机投影入口，公网预测逻辑不要直接塞进这里，另建 `prediction` 层。
- `server/room-lobby.mjs`：会话生命周期与 `SESSION_BUSY`/`SESSION_IDLE` 回收入口。

## 7. 当前边界

- 本机、局域网（`http://10.141.57.10:8787/`）和经 Frpc-Desktop/FRP 的公网测试入口（`http://39.108.93.52:10001/`）已做连通性验证；公网端口为 10001–10004，分别映射 viewer、lobby、authority、mirror。
- 公网浏览器端到端只验证了 Forest HTML5 的创建、加入和 authority WebSocket；Shanyi 公网镜像、刷新恢复、重复重开和长时间稳定性仍需继续验证。
- 没有 TLS、公网鉴权、DDoS 防护和跨区域部署，不能把“局域网可访问”或“单次公网连通”当作“公网可上线”。FRP token 只在本地客户端配置中，不进入浏览器。
- Shanyi 的公网表现未验证；HTML5 的预测/重连也还没有做公网级 E2E；公网入口仍应视为可信测试环境。
